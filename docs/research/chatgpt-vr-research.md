# Browser VR Workshop Palace for Meta Quest 2

## Bottom line

For this project’s actual constraints, the best first-build stack is **A-Frame on top of WebXR, with a static front end, modular custom components, glTF/GLB assets, and no backend until voice or shared memory truly requires one**. That recommendation is not because A-Frame is the most powerful option overall. It is because Meta explicitly positions WebXR as the right fit for lightweight experiences, prototypes, and web-distributed content, while A-Frame gives you the shortest path from “prompt an AI coding assistant” to “Quest-ready room with controllers, text, ray interaction, and static deployment.” A-Frame is HTML-first, uses an ECS architecture, sits on top of three.js, and already exposes the interaction primitives you need for a “Workshop Palace” MVP. citeturn14view4turn19search5turn3search0turn28search0turn37search0

The strongest alternative, if you outgrow A-Frame’s ergonomics, is **plain Three.js plus WebXR**, or **Meta’s newer Immersive Web SDK on top of Three.js** if you want a more structured modern stack for locomotion and spatial UI. Babylon.js is also a very capable browser-native choice, but it is usually a little slower to MVP when the builder wants static HTML-first iteration and heavy AI-assisted editing. PlayCanvas and Wonderland Engine are credible web-first engines, but both lean more editor-centric than your described workflow. Unity WebXR export and Godot WebXR can work, but for a Quest-browser-first static MVP they introduce more build complexity, more hosting caveats, and more browser-specific failure modes than they remove. citeturn25view0turn25view1turn29search2turn29search23turn7search13turn27search1turn31view0turn34view0

The design target should therefore be: **one lightweight hall, one camera rig, one interaction system, one room-manifest model, one clearly nonhuman companion presence, one GitHub Pages deployment, and one optional serverless secret-mint endpoint later for OpenAI voice**. Anything beyond that in version one is likely premature abstraction. citeturn16view0turn10search8turn11search0turn11search10

## Recommended version-one architecture

The right architecture for version one is **a static site with no application backend**, except for an optional tiny serverless function later when you add realtime AI voice or shared persistence. Meta’s own workflow docs emphasize that a WebXR experience is “just a normal web page,” which is exactly why this project should stay as boring as possible until you prove the interaction loop is worth expanding. citeturn16view0turn14view4

The scene should be structured as **one persistent world shell** rather than separate HTML pages for every room. In practice that means a single `<a-scene>` containing one rig, one global interaction layer, one room registry, and one top-level application state object. Rooms such as **Home**, **Artifacts**, **Projects**, **Reflections**, and **Notes** should be mounted as modular entities from separate files, then shown, hidden, or streamed as needed. A-Frame’s ECS model, systems, and component architecture are particularly useful here because they let you keep world logic, interaction logic, and content definition separate. citeturn3search0turn3search16turn28search9turn3search8

A good repository shape for AI-assisted work looks like this in spirit:

- `index.html` as the thin scene shell  
- `src/core/` for rig, routing, interaction, audio unlock, and state  
- `src/components/` for custom A-Frame components  
- `src/rooms/` with one file per room  
- `src/content/` with JSON manifests for artifacts, notes, and projects  
- `assets/models/`, `assets/textures/`, `assets/audio/`, `assets/fonts/`  
- `public/` only if you adopt a bundler later  

That structure matters because AI coding agents are much safer when asked to change **one room module** or **one content manifest** than when asked to rewrite a 1,500-line scene file. The implementation detail to protect most aggressively is the **core rig and interaction contract**; everything else should be pluggable. This is a design recommendation, but it is directly enabled by A-Frame’s component/system model. citeturn3search16turn28search9turn3search4

For navigation, version one should prefer **hub-and-room transitions** over free continuous traversal. Put the user in a central hall, let them see five destination cues, and send them either by teleport or by short portal transitions into each room. This avoids overbuilding locomotion, improves comfort, and simplifies content loading. Meta’s current locomotion guidance repeatedly emphasizes user comfort, predictability, and offering teleport plus snap-turn as sensible defaults. citeturn24search0turn24search1turn24search11turn25view1

For asset loading, use **A-Frame’s asset management system only for truly critical startup assets**: the first environment materials, the main font, one ambient loop, and maybe one small orb model. Everything else should be lazy-loaded when the user first approaches or enters a room. This is especially true for Projects and Artifacts, which are perfect candidates for on-demand GLB and texture loading. A-Frame’s asset system is explicitly for preloading and caching, but you do not want the initial scene blocked on every future room asset. citeturn3search4

Desktop fallback should be first-class even if Quest 2 is the target. A-Frame’s look-controls and wasd-controls give you a simple non-VR fallback path, while cursor/ray patterns can be made to work for both gaze and controller use. On phones, the experience should degrade to a simple 3D viewer or a 2D landing page with “best experienced in Quest Browser,” rather than forcing unsupported behavior. citeturn28search6turn28search3turn28search4

For deployment, GitHub Pages is entirely reasonable for the first iterations because the front end can remain plain static files. PlayCanvas’s docs say exported PlayCanvas apps are static content and can be hosted on GitHub Pages; Meta’s workflow docs say WebXR experiences are ordinary web pages served like any other site. The same logic applies to an A-Frame build made of HTML, JS, textures, audio, and GLBs. The larger point is not “use GitHub Pages forever,” but “don’t create infrastructure before the palace deserves it.” citeturn39view0turn16view0

Testing should follow a layered loop: **desktop browser with emulator**, then **local server on your machine**, then **Quest over ADB reverse or Wi‑Fi debugging**, then **remote Chrome inspection**, and finally **headset-only comfort checks**. Meta explicitly recommends Meta Quest Developer Hub for testing and debugging Browser content, documents `adb reverse` for local pages, and documents Chrome remote debugging through `chrome://inspect/#devices`. They also recommend the Immersive Web Emulator for desktop debugging without wearing the headset every iteration. citeturn14view5turn15view3turn15view1turn16view0

## Interaction and comfort guidelines

Version one should default to **controller ray interaction**, not direct hand-first interaction. A-Frame’s `laser-controls`, `cursor`, and `raycaster` are already designed for this model, and the docs explicitly note that `laser-controls` provides a consistent controller-ray interaction pattern across VR platforms. On Quest specifically, A-Frame’s `meta-touch-controls` wraps tracked controls with Quest controller mappings and models, which makes it an especially natural fit here. citeturn28search0turn28search4turn28search7turn37search0turn37search1

A gaze or reticle fallback still belongs in the system, but mostly as a backup for non-controller contexts and desktop/mobile preview. A-Frame explicitly documents the cursor component as usable for both gaze-based and controller-based interactions. That means your interaction model should be unified around a small set of events such as `hover`, `focus`, `select`, and `activate`, with controller rays as the primary transport. citeturn28search4turn37search4

For movement, the safest version-one default is **teleport plus snap turn**, with smooth locomotion either omitted entirely or placed behind a settings toggle once the space is already comfortable in teleport mode. Meta’s locomotion guidance calls out teleportation and snap turn as comfort-friendly defaults, and its newer web locomotion docs explicitly bias toward teleport plus snap turn out of the box, with slide and smooth turn as opt-in modes. Babylon’s WebXR docs make the same point bluntly: teleportation is the most convenient way to move without making users dizzy or disoriented. citeturn24search0turn24search1turn24search11turn25view1turn29search23

The most comfortable workshop-palace pattern is therefore not “walk through a huge museum,” but “short movement arcs between stable interaction zones.” The central hall should be visually spacious but mechanically shallow. Each room should have a safe standing position, one readable information surface, a few deliberate pickups or activations, and a clear return path. Meta’s comfort guidance also recommends keeping main controls consolidated, using distance interactions, and avoiding layouts that force unnecessary movement or extended reaching. citeturn24search12

Text and UI panels should be treated as performance and comfort problems, not as an afterthought. Meta’s rendering guidance recommends signed distance field fonts for easy reading in VR, and A-Frame’s text component already uses MSDF fonts by default. Meta’s typography docs advise comfortable reading sizes at 18px and up in conventional UI contexts, while the newer spatial UI docs emphasize crisp text, meter-based sizing, world-space panel placement, and avoiding per-frame canvas-texture updates. Put together, the practical guidance is: **use MSDF text, high contrast, short lines, minimal paragraph length, and large explicit panels**, not tiny floating labels scattered everywhere. citeturn24search13turn28search2turn23search16turn25view0

Selection targets should be large and forgiving, especially if you later add hand tracking. Meta’s accessibility guidance says visual targets should be at least 32dp by 32dp, and its hands guidance stresses that hand tracking quality can vary with lighting and that you should deliberately choose when to use ray, poke, or grab styles. That is another reason not to make hand tracking the primary interaction mode in version one: the palace concept benefits more from reliability than cleverness. citeturn24search9turn23search3turn23search15

Hand tracking is still worth planning for, but as an **optional secondary mode**. A-Frame, Babylon.js, and PlayCanvas all expose hand-tracking support, and A-Frame even documents hand-tracking controls and pinch-grab extras. But for Quest 2 specifically, hands should be treated as a later enhancement for simple, oversized interactions, not as the input foundation for fine UI manipulation. citeturn37search2turn37search12turn29search0turn7search2

Finally, audio should never be assumed to start automatically. Browser autoplay restrictions affect media and Web Audio, and both MDN and engine docs recommend a user gesture before resuming or starting audio. In practice, the palace should include a simple welcome interaction — trigger press, “Enter Workshop” button, or first portal activation — that unlocks the audio context and only then starts ambient audio or companion speech. citeturn9search0turn9search4turn33view0turn34view0

## AI presence and voice integration

The most effective first embodiment for the companion is **not a human avatar**. It is a **nonhuman, spatially anchored presence**: a moving orb, light cluster, small geometric familiar, or subtle emissive sculpture that can occupy space, turn toward points of interest, and speak from a clear location. That recommendation follows less from abstract aesthetics than from production reality. Human-like embodiments create animation, lip-sync, rigging, and expectation burdens that do not help an MVP. A nonhuman guide, by contrast, can feel intentional rather than unfinished. The browser stack already gives you the important part: spatial audio. A-Frame’s sound component is positional, and MDN’s Web Audio spatialization guidance notes that spatial audio is the correct primitive for realistic 3D sound. Research literature also suggests spatialized audio can play a meaningful role in social presence, even without strong visual realism. citeturn9search1turn9search19turn20search4turn20search15

A good companion design for version one has **five explicit states**: idle, noticing, listening, thinking, and responding. These should be communicated with motion, color, brightness, and sound rather than fake facial expressions. Idle can be a slow hover and ambient shimmer. Noticing can be a slight turn or pulse when the user nears an important object. Listening can be a visible change in waveform, glow, or ring size. Thinking can be a temporary dimming or orbiting particle effect. Responding can pair voice with a concise text panel. This is design synthesis rather than a documented requirement, but it fits the strengths and limitations of browser VR well. The key is to make the AI *present* without making it falsely *person-like*.

For dialogue display, use **voice plus mirrored text**, not voice alone. Voice alone in VR feels magical right up until the user misses one sentence. A small world-space caption or response panel near the companion solves that, improves accessibility, and gives the palace a “knowledge workspace” feeling rather than a disembodied smart-speaker feeling. Meta’s spatial UI guidance strongly favors world-space panels for immersive interactions and calls out crisp text as a core requirement. citeturn25view0

On the voice technology side, there are three practical classes of option.

The first is **browser-native Web Speech**. This is the simplest in theory and the least reliable in practice. MDN marks `SpeechRecognition` as limited availability, and current Quest developer reports indicate it may not be exposed in Meta Quest Browser. `SpeechSynthesis` exists and can work where device/browser voices are available, but voice inventory and output quality are browser-dependent. This means Web Speech can be a useful fallback experiment, but it is not reliable enough to serve as the foundation of your Quest Browser MVP. citeturn12search19turn12search0turn12search6

The second is **a chained browser pipeline**: capture mic audio with `getUserMedia`, send it to speech-to-text, send the transcript to a language model, then stream back generated speech. OpenAI’s current audio docs support exactly these pieces: request-based or streaming speech-to-text, text generation, and streamed text-to-speech. This route is easier to debug and easier to moderate than full speech-to-speech, but it is usually a bit higher-latency and feels more transactional. citeturn9search3turn10search1turn10search4turn10search7turn11search2

The third, and in 2026 the strongest option for a polished VR companion, is **OpenAI Realtime via WebRTC**. OpenAI’s current guidance is explicit: browser and mobile clients should connect to the Realtime API over **WebRTC**, the browser should get **ephemeral credentials** from a developer-controlled server, and standard API keys should not be exposed in client code. The docs also distinguish between direct speech-to-speech voice agents and chained pipelines, which is useful because your project may want to start chained and graduate to realtime later. citeturn11search0turn11search3turn11search10turn11search2turn11search19

That leads to the clean architecture pattern for this project:

**Static front end on GitHub Pages** → **tiny serverless endpoint you control** → **mint ephemeral client secret / apply rate limits / store optional session state** → **browser opens WebRTC session to OpenAI Realtime**. OpenAI’s key-safety docs explicitly advise against exposing API keys in browser code or public repositories, and the WebRTC docs show ephemeral key minting as the browser-safe path. citeturn10search8turn10search2turn11search0turn11search3

For version one, though, the wisest sequencing is to **separate “companion presence” from “live voice.”** Build the orb first, then give it scripted or local-state behaviors, then add text responses, then add server-backed voice. This keeps the revealing part of the experience — the sense of companionship in space — from being blocked by the hardest engineering piece.

## Asset pipeline and performance

The right asset philosophy for Quest Browser is **architectural beauty over asset mass**. Meta’s performance guidance is unusually clear on what hurts: overdraw, too many complex materials, too many real-time lights, real-time shadows, too many texture maps, and too much transparent content. It also emphasizes that performance is case-by-case and that you must measure on device rather than rely on folklore budgets. citeturn18view0

The canonical runtime asset format should be **glTF/GLB**. Khronos describes glTF as the runtime 3D asset delivery format designed for efficient transmission and loading, and Blender’s official glTF exporter is mature and directly oriented toward web/native interchange. For this project, that means: whatever generates the first concept shape — Blender, Spline, Meshy, Tripo, Luma, Blockbench, or something else — the asset should be normalized into **clean GLB exports** before it becomes part of the palace. citeturn35search0turn35search8turn36search1

The texture strategy should start simple and become more technical only when needed. Meta’s Quest WebXR performance docs recommend **KTX 2.0 / Basis Universal** for texture compression, because it reduces in-memory texture size and improves GPU efficiency on Quest. three.js has `KTX2Loader`, and A-Frame can still benefit because it sits atop three.js. For textures, this is one of the highest-value optimizations you can make once the scene stops being pure primitives. citeturn18view0turn6search0turn35search6turn35search2

Geometry compression is useful, but should be applied with a little skepticism on Quest-class hardware because smaller downloads can mean more decode work. three.js supports Draco, and meshopt-based glTF compression is explicitly designed to reduce file size while keeping fast decoding. The practical rule is: **compress hero assets that matter, but do not blindly pipeline everything through every compressor**. Texture compression usually pays back first; geometry compression pays back when download size is the actual bottleneck. citeturn5search2turn35search7turn35search14

The lighting and material plan for the palace should reflect Meta’s performance guidance almost literally. Use **one dominant directional light at most**, prefer static lighting moods, bake where possible, avoid dynamic shadows in version one, and use PBR sparingly. Meta explicitly warns that each extra light increases shader cost, that shadows multiply draw-call and triangle costs, and that multiple PBR maps increase texture bandwidth pressure. citeturn18view0

That is why the first beautiful version of the palace should come from:

- strong large-scale forms  
- carefully chosen emissive accents  
- atmospheric fog or gradient sky  
- audio and spatial composition  
- a few beautiful wall textures or “memory panels”  
- repeated modular geometry  
- minimal transparency  
- crisp text and clean layout  

rather than from cluttered hero meshes or dynamic lighting tricks. This is the browser-VR equivalent of good stage design: focal points matter more than object count.

Generated images can be very useful here, but mostly as **surface language**, not as 3D geometry. AI concept art can become mural textures, framed artifact plates, note-wall papers, skybox references, or emissive window pieces. That gives the palace atmosphere without forcing low-quality generated 3D into the runtime. When you *do* use generated 3D, route it through Blender cleanup: remove hidden geometry, simplify materials, merge meshes where appropriate, atlas textures, and export a clean GLB master.

A sensible pipeline for the first few prototypes is therefore:

**Primitives first** → **clean low-poly modular kit** → **GLB room props** → **compressed textures** → **selected hero assets optimized with Draco or meshopt if needed**.

That sequence specifically reduces the chance that aesthetics become hostage to premature pipeline complexity.

## Current limitations and the most reliable development workflow

The biggest technical limitation to keep in mind is not “WebXR is weak.” It is “**browser VR is unforgiving about assumptions**.” Meta’s own docs say WebXR is excellent for lightweight experiences, but native remains preferable for performance-intensive work and deep platform integration. That means your palace can work very well in Browser as long as you deliberately stay inside that product envelope. citeturn7search18turn14view4

A second limit is that the browser itself is evolving. Meta Browser release notes for version 146 mention **experimental WebGPU support in WebXR** and in-browser depth projection, which is interesting but exactly the kind of thing you should not build version one around. Experimental support is a signal to watch the platform, not a green light to anchor an MVP to bleeding-edge features. citeturn14view1

Permissions and secure-context rules matter immediately once voice enters the picture. MDN documents that `getUserMedia()` is only available in secure contexts, and current engine docs for Unity and Godot likewise call out browser authorization and secure-context requirements around microphone and audio behavior. In practice: if you want mic access, use HTTPS in production and a proper local testing setup in development, not `file://`. citeturn9search3turn33view0turn34view0

CORS and host behavior also matter more than many WebXR tutorials admit. Unity’s web networking docs explicitly say cross-origin resources need CORS authorization, and Godot’s web docs note same-origin policy restrictions and the lack of low-level networking. Even if you are not using Unity or Godot, the browser rules they describe apply to the same platform you are targeting. If your GLBs, textures, or API endpoints come from another origin, expect to configure them deliberately. citeturn31view1turn34view0

For local development and Quest testing, the productive loop is already documented by Meta: use MQDH when possible, use ADB reverse to view your local desktop server from the headset, use Wi‑Fi debugging only when needed, and use Chrome remote inspection for real browser debugging. Pair that with the Immersive Web Emulator on desktop so that most layout and interaction regressions are caught before you ever put the headset on. citeturn14view5turn15view3turn15view1turn16view0

For AI coding agents, the safest workflow is to make them operate on **bounded, named surfaces**. Ask them to change `rooms/home.js`, not “the whole scene.” Ask them to alter the `artifactManifest.json`, not “the app’s data logic.” Ask them to extend the `companion-orb` component, not “the interaction system.” This is not a platform fact so much as a maintainability rule, but it pairs especially well with A-Frame’s ECS structure and keeps the repo legible to both humans and models. citeturn3search0turn3search16turn28search9

The small automated checks worth having from the beginning are mundane but powerful: desktop load with no console errors, Quest Browser load, controller ray still visible, room manifest valid JSON, lazy-loaded asset path exists, and no change to the core rig or interaction selectors unless explicitly intended. In browser XR, regression prevention is often worth more than another feature.

Use **A-Frame for the first build**.
