The primary driver behind this selection is the declarative nature of A-Frame's HTML syntax. Natural-language AI coding agents possess extensive training on DOM manipulation and HTML structures. By instructing an AI agent to build a scene using semantic tags like <a-scene>, <a-box>, or <a-entity>, the developer avoids the friction of generating hundreds of lines of imperative Three.js or Babylon.js boilerplate.Furthermore, A-Frame adheres strictly to an Entity-Component-System (ECS) architecture. This architectural pattern is fundamentally modular. Entities are empty containers, and components are isolated JavaScript logic blocks that attach to those entities to provide behavior, appearance, or functionality. This isolation allows an AI coding assistant to generate or modify a single component (e.g., a custom script for portal traversal) without altering the global state of the application. The AI agent acts upon the machine-readable representation of the site (the DOM) with high precision.Engines that rely on visual editors and WebAssembly (WASM) compilation, such as Unity, Godot, PlayCanvas, or Wonderland Engine, actively work against the text-based nature of current LLM coding workflows. The generated output of a Unity WebGL export is a massive, opaque binary file. An AI agent cannot incrementally debug or modify C# logic that has been flattened into WASM. Similarly, React Three Fiber (R3F) provides declarative syntax, but introduces the overhead of React's virtual DOM reconciliation and requires a Vite/Webpack build pipeline. For an initial MVP that prioritizes lightweight, rapid deployment via GitHub Pages, the absence of a required build step in plain A-Frame is a massive operational advantage.2. Recommended System Architecture for the MVPTo satisfy the requirements of a practical, lightweight WebXR workspace that hosts a dynamic AI companion while remaining deployable via GitHub Pages, the system architecture must aggressively decouple the static presentation layer from the secure, stateful AI backend logic. Hosting the application on GitHub Pages imposes a strict "static-only" constraint on the frontend. The repository can serve HTML, CSS, JavaScript, and optimized 3D assets (GLB files, textures), but it cannot execute server-side code, run Docker containers, or securely store API keys.Exposing an OpenAI API key within client-side JavaScript deployed on GitHub Pages is a catastrophic security vulnerability. Any user could inspect the browser console, view the network requests, and siphon the key for unauthorized, potentially expensive use. Therefore, a hybrid architecture is absolutely mandatory. The architecture is bisected into a static frontend (The Palace) and a lightweight proxy backend (The Gatekeeper).2.1 The Static Frontend (GitHub Pages)The frontend utilizes A-Frame to render the stereoscopic WebGL environment. It manages the asset loading pipeline, local device tracking (headset pose, controller input), spatial audio rendering, and UI interactions. The frontend is entirely stateless between sessions unless utilizing the browser's native localStorage or IndexedDB APIs to persist minor user preferences or the state of the Artifacts room.Because rendering a monolithic HTML file containing the geometry for all five rooms (Home, Artifacts, Projects, Reflections, and Notes) would quickly exceed the memory limitations of the Quest 2 browser, causing crashes or severe frame drops, the architecture must utilize dynamic scene loading. The A-Frame <a-scene> element serves as the constant global root. Within this root, a central container entity holds the current room's assets. When the user interacts with a portal or door to transition between rooms, a custom JavaScript component intercepts the event. It triggers a camera fade-to-black effect, dynamically removes the previous room's DOM elements (e.g., container.innerHTML = ''), fetches the new room's HTML fragment via fetch(), injects it into the DOM, and fades the camera back in. This approach ensures that only the polygons and textures required for the immediate visual vicinity are loaded into the GPU's memory at any given time.The asset loading system must leverage A-Frame's <a-assets> tag. By preloading heavy textures, audio files, and 3D models into browser memory before they are injected into the visual scene, the architecture ensures that room transitions do not cause rendering stutters (which occur when asynchronous network requests block the browser's main thread). Furthermore, the architecture naturally supports a desktop/mobile fallback. Because A-Frame automatically provides a "magic window" desktop mode with WASD keyboard movement and mouse-look controls, the application remains fully accessible for testing, debugging, and usage outside the VR headset.2.2 The Backend ProxyFor an MVP, the backend does not need to handle high-bandwidth audio streaming or complex database routing. Instead, it serves a single primary function: minting ephemeral tokens for the OpenAI Realtime API. By deploying a minimal Node.js Express server on an inexpensive platform (such as Render, Heroku, or a serverless function), the backend securely holds the master OpenAI API key in its environment variables.When the frontend client initializes the AI companion, it sends an HTTP POST request to this backend endpoint. The backend negotiates with OpenAI's REST API to generate a short-lived, limited-scope ephemeral token, which it returns to the client as a JSON response. The frontend then uses this ephemeral token to establish a direct WebRTC peer-to-peer connection with OpenAI's servers. This architectural choice is highly optimized; it completely offloads the heavy processing of real-time audio streaming from the developer's infrastructure directly to OpenAI, eliminating proxy latency and reducing server bandwidth costs to near zero.3. WebXR Interaction Design on Meta Quest 2Designing interactions for virtual reality demands strict adherence to physiological and ergonomic constraints. The Meta Quest 2 utilizes six-degrees-of-freedom (6DoF) inside-out tracking and physical motion controllers. The interaction paradigm for the WebXR workspace must prioritize user comfort, intuitive navigation, and precise object selection without inducing simulation sickness.3.1 Locomotion and ComfortLocomotion is the primary vector for VR discomfort. Smooth artificial locomotion, where the user glides continuously across the virtual floor using the controller thumbstick, creates a severe sensory conflict. The visual system perceives motion, but the vestibular system in the inner ear detects that the body is stationary. This mismatch rapidly induces nausea in a significant percentage of users. Therefore, teleportation must be implemented as the default navigation mechanic.The aframe-blink-controls component is the standard, battle-tested solution for A-Frame WebXR projects targeting the Quest 2. It provides a parabolic raycaster attached to the user's controller. When the user pushes the thumbstick forward, the ray calculates a geometric intersection against designated floor meshes. Upon release, the camera is instantaneously transported ("blinked") to the target location, bypassing the visual translation that causes sickness. Crucially, this component also supports snap-turning, allowing the user to rotate their virtual orientation in discrete 45-degree increments using lateral thumbstick movements. This eliminates the need for users to physically spin in their physical space, accommodating seated or front-facing setups safely.3.2 Object Selection and Hand TrackingFor object interaction within the various rooms (such as picking up artifacts or selecting UI panels), controller raycasting is highly recommended over gaze-based interaction or direct hand tracking for the initial MVP. Gaze interaction forces the user to awkwardly point their head at targets to trigger a dwell-timer, leading to severe neck strain over prolonged sessions. Hand tracking, while supported natively by WebXR on the Quest 2 via the Hand Input API, introduces significant complexity. Hand tracking is frequently occluded when hands cross or rest near the body, and gestures lack the definitive haptic feedback provided by physical controller buttons.Attaching A-Frame's standard raycaster and laser-controls components to the left and right controller entities provides a precise, laser-pointer style interface. To maintain the critical 72 FPS performance target, the raycaster must be explicitly configured to only intersect with objects possessing a specific class (e.g., raycaster="objects:.interactable") rather than the entire scene geometry. If this is not constrained, the JavaScript intersection loop will consume excessive CPU cycles checking every polygon in the environment on every single frame, leading to catastrophic performance degradation.3.3 Readable Text in VRText legibility represents a major historical hurdle in WebXR. The native resolution of the Quest 2 display combined with the optical distortion of the Fresnel lenses means that standard, low-resolution texture-based text quickly becomes an unreadable, pixelated blur. A-Frame's default text component utilizes Multi-channel Signed Distance Fields (MSDF), which scales well but requires the cumbersome process of pre-generating texture atlases for every font and character set required. In a workspace where an AI companion generates dynamic, unpredictable text responses, pre-baking glyphs is impossible.The architecture must instead utilize the aframe-troika-text library. This component reads raw TrueType (TTF) or OpenType (OTF) font files directly and leverages a background web worker to generate Signed Distance Field (SDF) geometries on the fly, preventing main-thread blocking. This approach yields razor-sharp text at any distance, scale, or viewing angle. It fully supports dynamic string injection, automatic line wrapping, kerning, and advanced typographic features like ligatures, allowing the integration of UI icon fonts seamlessly. By integrating aframe-troika-text, the UI panels floating within the workspace can display the AI's generated insights, project notes, and system menus with perfect clarity.3.4 Audio Unlock RequirementsA critical interaction constraint involves modern browser autoplay policies. Browsers, including the Quest Browser, aggressively block audio playback (including Web Audio API AudioContext nodes and HTML5 <audio> elements) if the user has not explicitly interacted with the document via a user gesture, such as a click or tap. If the audio context is not unlocked, the AI companion will be entirely silent.WebXR applications elegantly bypass this restriction through their entry mechanism. The user is required to physically click an "Enter VR" button on the 2D webpage interface to transition the browser into the immersive stereoscopic WebXR session. This initial, mandated click satisfies the browser's user-interaction requirement. The developer must ensure that the application's global AudioContext.resume() is called immediately within the event listener attached to that "Enter VR" click, ensuring the audio pipeline is fully unlocked before the user ever sees the inside of the 3D palace.4. AI Presence and Companion DesignThe introduction of an AI companion into a spatial computing environment introduces complex user experience challenges. Attempting to represent the AI as a photorealistic or stylized humanoid avatar frequently plunges the experience into the uncanny valley—a psychological phenomenon where near-human entities provoke feelings of eeriness or revulsion. Humanoid avatars require complex, real-time inverse kinematics (IK) for natural limb movement, sophisticated lip-syncing algorithms tied to audio output, and subtle procedural idle animations (blinking, shifting weight) to avoid appearing as a lifeless mannequin. These requirements heavily tax the Quest 2's mobile processor, drain battery life, and vastly exceed the scope of an MVP. Furthermore, assigning human forms to AI can create misaligned user expectations regarding the system's emotional capacity, empathy, and actual cognitive understanding.A highly effective, performance-friendly alternative involves embracing the non-human nature of the intelligence. Representing the AI companion as a volumetric light anomaly, an abstract geometric constellation, or a pulsating energy orb bypasses the uncanny valley entirely while conveying a sense of advanced, alien capability. From a technical standpoint, this abstract approach is vastly superior. An orb can be rendered using a simple <a-sphere> entity paired with a custom GLSL (OpenGL Shading Language) shader material. This shader modulates vertex displacement and fragment color based on procedural mathematics like Perlin noise, or more importantly, incoming audio frequency data. When the AI speaks, the amplitude of the incoming audio stream can be passed as a uniform variable directly to the GPU shader. This causes the orb to visibly pulsate, expand, and shift colors dynamically in perfect synchronization with its voice, providing immediate, undeniable visual feedback that the entity is communicating. This entirely replaces the need for complex, CPU-bound lip-syncing.To anchor this abstract visual representation in the physical space of the virtual palace, the system must leverage advanced spatial audio capabilities. The Web Audio API provides the PannerNode, a sophisticated digital signal processing unit that mathematically simulates how sound behaves in three-dimensional space. When the AI speaks, its incoming WebRTC audio stream is routed through a PannerNode whose X, Y, and Z coordinates are strictly locked to the visual position of the orb.As the user navigates the workspace, the Web Audio API automatically calculates interaural time differences (the microsecond delay between a sound hitting the left ear versus the right ear) and volume attenuation based on the user's head tracking data. The A-Frame wrapper for this functionality is the <a-sound> component, but for real-time WebRTC streams, custom JavaScript is required to attach the incoming MediaStreamTrack to a THREE.PositionalAudio object. The attenuation should be configured using an inverse distance model, which calculates the gain reduction mathematically :$$\text{Gain} = \frac{\text{refDistance}}{\text{refDistance} + \text{rolloffFactor} \times (\max(\text{distance}, \text{refDistance}) - \text{refDistance})}$$By utilizing this inverse distance mathematical model, the AI's voice will appropriately diminish in volume as the user walks to a different corner of the room, and shift smoothly between the left and right stereo channels as the user turns their head. This seamless, latency-free integration of reactive abstract visuals and physically accurate spatial audio triggers a profound sense of "presence"—the psychological illusion that the AI is genuinely occupying the geometric space alongside the user.5. Voice and AI Integration WorkflowSeamless, low-latency verbal communication is the cornerstone of an effective AI-human collaboration workspace. Traditional web-based voice assistants utilize a slow, sequential pipeline: the browser captures audio, sends it to a Speech-to-Text (STT) service, passes the resulting text to an LLM, sends the text response to a Text-to-Speech (TTS) service, and finally streams the generated audio back to the client. This pipeline routinely incurs latencies of 3 to 5 seconds. This delay destroys natural conversational flow and constantly reminds the user they are interacting with a machine over a slow network, breaking the illusion of presence.Furthermore, relying on the browser's native Web Speech API (for client-side STT dictation) is non-viable for this project. Extensive developer testing confirms that the Meta Quest Browser does not currently expose the Web Speech API (SpeechRecognition) to web applications, rendering native, offline dictation impossible within the headset.The definitive solution is the integration of the OpenAI Realtime API utilizing the WebRTC protocol. This protocol establishes a continuous, bidirectional, low-latency peer-to-peer connection. The OpenAI Realtime model natively processes incoming audio waveforms and generates outgoing audio waveforms simultaneously, completely bypassing the intermediate text steps. This reduces response latency to a few hundred milliseconds and allows for natural conversational dynamics, including the critical ability for the user to interrupt the AI mid-sentence simply by speaking over it.Implementing WebRTC within a browser-based WebXR environment involves a specific sequence of operations:Token Generation: As established in the architecture section, the frontend executes a REST request to the developer's backend Node.js proxy to mint an ephemeral token.WebRTC Initialization: The client creates a new RTCPeerConnection object. To successfully traverse network Address Translation (NAT) routers and firewalls, the connection utilizes public STUN servers (e.g., stun:stun.l.google.com:19302).Media Capture: The application requests microphone access via navigator.mediaDevices.getUserMedia(). Because the captured audio is being fed into a highly sensitive AI model, the input must be strictly pristine to prevent the AI from hallucinating on background noise. The constraints object must explicitly enforce echoCancellation: true, noiseSuppression: true, autoGainControl: true, and define a sampleRate of 24000 Hz, which aligns perfectly with OpenAI's expected optimal input format.Data Channel Creation: Alongside the primary audio track, an RTCDataChannel is instantiated. This secondary channel transmits and receives JSON events in real-time. It handles the real-time text transcription of the conversation (which can be displayed on aframe-troika-text UI panels), connection status updates, and functional commands (e.g., the AI signaling the system to spawn a 3D model in the Artifacts room).SDP Handshake: The client generates a Session Description Protocol (SDP) offer, characterizing its media encoding capabilities. This offer is sent via a standard HTTP POST request directly to the OpenAI Realtime endpoint (api.openai.com/v1/realtime), authorized purely by the ephemeral token. OpenAI replies with an SDP answer, which the client accepts as the remote description, successfully bridging the WebRTC connection.Once the connection is live, the incoming remote audio stream is intercepted, prevented from playing flatly over the global audio output, and instead routed directly into the A-Frame audio graph using THREE.AudioContext, attaching the stream to the visual orb representation as discussed previously.6. Asset Creation and Optimization PipelineThe visual fidelity of the VR Workshop Palace is inextricably bound by the strict hardware limitations of the standalone Meta Quest 2 headset. The device is powered by a mobile Snapdragon XR2 processor. Pushing complex WebGL scenes through a browser wrapper introduces additional overhead compared to native, compiled applications. To maintain a comfortable, non-nauseating framerate of 72Hz or 90Hz, developers must ruthlessly optimize the rendering pipeline.The absolute ceiling for WebXR performance on the Quest 2 dictates a maximum of 100 to 200 draw calls per frame, and a total polygon count not exceeding 500,000 to 1,000,000 triangles. Every unique material and every distinct mesh object in a Three.js/A-Frame scene triggers a separate draw call, instructing the CPU to communicate state changes to the GPU. If a scene contains a virtual bookshelf with 200 individual books, each utilizing a separate material, the draw call limit is instantly obliterated. The CPU will bottleneck, resulting in catastrophic framerate drops.To circumvent these strict constraints while achieving the aesthetic of a grand, inspiring "palace," the asset pipeline must rely heavily on illusion rather than explicit geometry. The foundation of the environment should be built using basic primitive geometry (planes, cylinders, and boxes) constructed natively in A-Frame.To provide the illusion of vast, intricate architecture beyond the walkable boundaries, the project must utilize generative AI image tools (such as Midjourney or Stable Diffusion) to generate equirectangular panoramic images. These 360-degree images are mapped to an <a-sky> entity, projecting a photorealistic, high-resolution backdrop of an expansive palace interior or cosmic vista. Because the skybox is a single inverted sphere with exactly one texture applied, it costs exactly one draw call and a negligible number of triangles, yet visually fills the user's entire peripheral vision with stunning detail.For the physical boundaries of the room (floors, walls, pedestals) and the objects within the Artifacts room, 3D assets should be sourced from lightweight creation tools like Spline, Blockbench, or AI 3D generators (Meshy, Tripo, Luma). These assets must be exported strictly in the GLB (Binary glTF) format. GLB is the universally optimal format for WebXR; it packages the 3D geometry, textures, and material definitions into a single, highly compressed binary file, significantly accelerating network transmission and browser parsing.Before deployment to GitHub Pages, these assets must be subjected to an optimization pipeline. All static objects within a room should be merged into a single monolithic mesh where possible. All individual textures must be baked into a single texture atlas, allowing multiple objects to share one material, thereby reducing dozens of draw calls down to a single instruction.Furthermore, real-time dynamic lighting and shadows must be entirely abandoned for the MVP. Calculating real-time shadows involves rendering the entire scene multiple times from the perspective of each light source, instantly crippling the mobile GPU. Instead, ambient occlusion, global illumination, and shadow information must be "baked" directly into the base color textures of the GLB models within a software package like Blender. The corresponding A-Frame materials are then set to shader: flat or configured to ignore scene lighting entirely. By relying on unlit materials, texture atlases, and AI-generated equirectangular skyboxes, the application will comfortably maintain 90 FPS while presenting a visually striking environment.7. Current WebXR Limitations and GotchasDeveloping for the immersive web presents unique deployment and testing challenges not found in traditional 2D web development. Awareness of these specific "gotchas" prevents days of wasted engineering effort.7.1 Secure Contexts and Local TestingThe WebXR Device API is strictly gated behind secure contexts. A browser will utterly refuse to expose the API or display the "Enter VR" button if the site is served over standard HTTP (with the sole exception of http://localhost). During local development, viewing the scene on the desktop monitor works flawlessly over localhost, but viewing it inside the Quest 2 headset requires navigating to the developer machine's local IP address over the Wi-Fi network (e.g., 192.168.1.50:8080). Because this is an IP address and not "localhost", the Quest Browser treats it as an insecure context and disables WebXR completely.To test locally inside the headset, developers must establish a local Certificate Authority. The established workflow involves utilizing the mkcert command-line tool to generate locally trusted SSL certificates. These certificates are then fed into a tool like local-ssl-proxy, which wraps the local development server in an HTTPS layer. The Quest headset is then forced to trust the certificate, allowing WebXR initialization over the local network.7.2 Debugging the Quest BrowserWhen a JavaScript error occurs within the headset, the Quest Browser does not inherently display a visible developer console. Guessing the cause of a silent failure, especially during complex WebRTC handshakes, is highly inefficient. The standard debugging workflow requires connecting the Quest 2 to the development PC via a USB-C cable (or establishing ADB over Wi-Fi), enabling "USB Debugging" on the headset, and opening the special URI chrome://inspect/#devices on the desktop Chrome browser.This bridges the connection, opening a full, remote Chrome DevTools panel on the desktop that is directly tied to the active Quest Browser tab. Developers can inspect the DOM, monitor network requests, view console.log outputs, and step through JavaScript breakpoints while physically wearing the headset. This connection can occasionally be flaky, dropping the device from the list; restarting the ADB server via the command line (adb kill-server followed by adb start-server) usually resolves the disconnect.7.3 GitHub Pages and CORS ConstraintsWhile GitHub Pages is ideal for hosting the static MVP, it relies on global Content Delivery Networks (CDNs) that enforce specific caching rules. 3D assets (GLB files) and audio files are often heavily cached. If a model is updated and pushed to the repository, the browser may aggressively serve the stale cached version. Implementing cache-busting techniques, such as appending dynamic query strings to asset URLs in the HTML (e.g., src="model.glb?v=1.2"), ensures the latest assets are always downloaded.Additionally, GitHub Pages does not support custom backend routing. Therefore, single-page application (SPA) routing mechanisms used to manage the virtual rooms must rely on hash-based routing (/#/reflections-room) rather than standard path routing to prevent 404 errors upon direct navigation. Furthermore, if the application attempts to load textures or GLBs from external domains (e.g., an image hosting site), the external server must have explicit Cross-Origin Resource Sharing (CORS) headers enabled, otherwise the WebGL renderer will block the texture from loading for security reasons.8. Development Workflow with AI Coding AgentsBuilding this spatial project exclusively with natural-language AI coding assistants (such as Claude, Cursor, or Windsurf) requires deliberate repository structuring. Large Language Models possess massive context windows, but feeding an agent a monolithic 3000-line HTML file containing the entire palace, logic, and styling induces severe hallucination, context degradation, and high token costs.The repository must enforce strict modularity. The structure should separate concerns distinctly:/index.html (Minimal entry point, containing only the <a-scene>, asset preloading, and camera rig)./components/ (A folder containing isolated .js files for custom A-Frame components, e.g., portal-logic.js, orb-visuals.js, webrtc-audio.js)./rooms/ (A folder containing .html fragments representing the entities for each room)./assets/ (Textures, GLBs, audio files).To maximize the efficacy of AI coding agents, the project should utilize context alignment files. Modern AI IDEs support reading files like CLAUDE.md, .cursorrules, or llms.txt automatically. The developer must place a set of strict rules in the root directory instructing the AI on the specific syntax, versioning, and constraints of A-Frame 1.7.1.A highly effective prompt instruction set (placed in .cursorrules) for the agent would include:Always write declarative A-Frame HTML instead of imperative Three.js when adding objects to the scene.Register all custom logic using AFRAME.registerComponent. Never use inline script tags inside the HTML body. Assume the target is Meta Quest 2. Limit geometries to primitives where possible and strictly limit draw calls.Do not attempt to import massive npm packages for the frontend; rely on standard browser APIs and CDN scripts to maintain GitHub pages compatibility.When generating text, utilize aframe-troika-text, not the default A-Frame text component.When tasking the agent, the workflow should proceed incrementally. Rather than requesting, "Build the VR palace with an AI companion," the prompt should be hyper-specific and scoped to a single file: "Create a new A-Frame component in /components/teleport.js that attaches aframe-blink-controls to the camera rig, allowing intersection only with entities possessing the class nav-mesh.". By scoping requests to individual components or HTML fragments, the AI returns highly accurate, bug-free code that securely slots into the broader, modular architecture.9. Final Recommendations and Next StepsThe objective of building an immersive, browser-based AI-collaboration workspace for the Meta Quest 2 is highly achievable, provided strict adherence to architectural constraints is maintained throughout development.Definitive Stack Recommendation:
The first build must utilize A-Frame 1.7.1 for the frontend WebGL rendering, hosted statically on GitHub Pages. This guarantees alignment with LLM coding agents, ensuring rapid, text-driven iteration. The AI voice system must bypass native browser limitations by utilizing the OpenAI Realtime API over WebRTC. Because GitHub Pages cannot secure secrets, a separate lightweight Node.js backend must be deployed on an inexpensive cloud host solely to generate WebRTC ephemeral tokens, completely protecting the OpenAI API keys from client-side exposure.Architectural Traps to Avoid:Avoid Heavy Game Engines: Do not attempt to export Unity or Godot to WebGL for this MVP. The payloads are massive, performance on mobile browsers is poor, and AI coding agents cannot assist in modifying the compiled WASM binaries.Avoid Humanoid Avatars: Do not attempt to implement humanoid AI companions with lip-syncing and inverse kinematics. It will crush the Quest 2's framerate and plunge the experience into the uncanny valley. Utilize abstract, audio-reactive orbs synchronized with spatial audio.Avoid Massive Single-File DOMs: Do not load all rooms (Home, Artifacts, Reflections) simultaneously. Actively swap DOM elements using JavaScript during camera fades to stay below the strict 100-200 draw call limit.Avoid Standard Text: Do not use default texture-based text. It will render illegibly in the headset. Implement aframe-troika-text immediately for crisp, SDF-based dynamic typography.Smartest First Implementation Step:
The absolute first technical step is establishing the local development and testing pipeline. Before writing a single line of 3D logic, the developer must configure mkcert and local-ssl-proxy on their development machine. Achieving a secure HTTPS local network connection is the only way to test WebXR natively inside the Quest 2 browser over Wi-Fi. Once the local network can serve a simple <a-scene> containing a single cube to the headset at 72Hz, the architectural foundation is secure, and Prototype 0 is complete. From there, the developer can confidently unleash the AI coding agents to systematically construct the logic, rooms, and intelligence of the VR Workshop Palace.
